# The game side: `hlap`

A Half-Life server dll, built from Valve's own SDK, that talks to the
Archipelago client through the file bridge in `<Half-Life>/hlap/archipelago/`.

**Status: it runs and a seed is playable.** Phase 0 is done. The dll builds
32-bit with MSVC, installs through `tools/install_mod.py`, and in play: the mod
loads, the hub comes up, `ap_warp` travels, checks fire and reach the server,
items arrive and are announced, pickups are refused until the multiworld sends
them, saves and level transitions work.

Not yet confirmed in play: the mission-boundary interception, the finale's seal,
DeathLink in either direction, and the traps beyond Butterfingers.

The headless route, `hlds.exe -game hlap +map c0a0`, is not available: the
dedicated server shipped inside a Steam client install cannot mount its
filesystem, and the stock `valve` game fails identically, so it says nothing
about this dll either way. Test in the real client.

## Why a dll rather than a plugin

Valve's [ValveSoftware/halflife](https://github.com/ValveSoftware/halflife)
repository tracks the 25th anniversary game, so a dll built from it is the
shipped game's own logic rather than the 2003 SDK's. That is what makes this
acceptable to a player who specifically wants the original game, and it gives
full C++ class access -- `GiveNamedItem`, `RemovePlayerItem`, `PlayerUse`,
`CanHavePlayerItem` -- with no third-party dependency.

The mod folder inherits everything else through `fallback_dir "valve"`, so the
player's install is never written to. See `apworld/half_life/mod/` for the
installer and `liblist.gam`.

## Building

**MSVC, and it has to be MSVC** -- see "Why not MinGW" below. Any Visual Studio
2022 with the C++ workload will do; Build Tools is enough.

    git clone https://github.com/ValveSoftware/halflife.git ../halflife
    git -C ../halflife apply ../hl1-anniversary-ap/game/sdk.patch
    cmake -S game -B build/game-msvc -A Win32 -DHLSDK_DIR=../halflife
    cmake --build build/game-msvc --config Release

The result is `hl.dll`, about 1.3 MB, which goes to
`<Half-Life>/hlap/dlls/hl.dll`. Dropping it into
`apworld/half_life/mod/files/dlls/` makes the apworld install it for the player;
that path is gitignored, so a development checkout installs everything but the
dll and the client says so.

32-bit is not optional: GoldSrc loads a 32-bit dll.

Two things the CMakeLists does that are worth knowing:

- **The CRT is static** (`/MT`). Linked against the dynamic one, the dll needs
  the 32-bit VC++ redistributable on the player's machine and fails with
  `LoadLibrary failed (126)` without it -- ERROR_MOD_NOT_FOUND, naming nothing.
  Statically linked, `KERNEL32.dll` is the only dependency.
- **`GiveFnptrsToDll` is exported by hand**, with
  `/EXPORT:GiveFnptrsToDll=_GiveFnptrsToDll@8`, rather than through the SDK's
  `dlls/hl.def`. eiface.h makes that function `__stdcall` and does not mark it
  exported, and leaving the linker to match an undecorated name in a `.def`
  against a decorated symbol failed on a build that differed only in its CRT.

`sdk.patch` was generated by editing a clean clone, so it applies cleanly by
construction: 46 added lines across eight files, one `#include` and one call per
hook, nothing of Valve's deleted. Keeping it that small is the point -- the less
this project edits Valve's files, the less a future SDK update costs.

### Why not MinGW

It was built with MinGW first, and that build loads, runs, and executes the whole
hook chain -- which is what proved the design before any MSVC toolchain was
available. It also **cannot save**, and in GoldSrc that means it cannot cross a
level transition either, because transitions run through the same save/restore
machinery.

The engine saves an entity's think, touch and use functions *by name*: saving
asks it for the name of a function address, loading asks for the address of a
name, and both go through the dll's export table. With the MinGW build it cannot
do the lookup. The symptoms, in order of appearance: a flood of
`Can't find address:` on every save, those functions written to the save file as
empty strings, and `PF_precache_model_I: Bad string ''` when the save is read
back -- which is every quickload and every level transition in the game.

Our export table is not obviously wrong (978 names against Valve's 992, all the
right ones present), so the mismatch is in how the addresses line up rather than
in what is exported. `-Wl,--export-all-symbols` makes it worse, not better: the
table goes to 9,976 names and the engine, which resolves map entities by
`GetProcAddress(dll, classname)`, crashes on map load instead. `-fno-ipa-icf`
changed nothing.

The MinGW branch of the CMakeLists is kept, working, for that reason -- it is a
useful second opinion if MSVC ever misbehaves -- and these are what it costs:

- `cbase.h` and `util.h` spell the export attribute `_declspec`, which is MSVC
  only. Both sit behind an `#ifndef`, so the CMakeLists defines
  `CBASE_DLLEXPORT` and `UTIL_DLLEXPORT` to `__declspec(dllexport)` for
  non-MSVC and Valve's headers are untouched.
- `common/mathlib.h` has an MSVC inline-asm block behind `#ifdef _WIN32`, with a
  portable C branch right beneath it. `sdk.patch` narrows that to
  `defined(_WIN32) && defined(_MSC_VER)`, so MSVC keeps the asm and everyone
  else gets the C. This is the only patch hunk that is not a hook.
- gcc 16 defaults to C23, where `false` is a keyword and `const.h` uses it as an
  enumerator, so the three `pm_shared` C files are built as `gnu17`.
- GNU ld cannot parse the `SECTIONS .data READ WRITE` clause at the end of the
  SDK's `dlls/hl.def`, so the MinGW build uses `hl_mingw.def` instead. See the
  comments in that file: it exists for exactly one export.
- The link is fully static for the same reason MSVC's is, and
  `-static-libgcc -static-libstdc++` is not enough: the posix-threads build of
  gcc still imports `libwinpthread-1.dll`.

## Layout

| File | What it owns | Where it attaches |
| --- | --- | --- |
| `src/ap_main.*` | wiring, the poll clock, the façade the patch calls | `ServerActivate`, `StartFrame` |
| `src/ap_bridge.*` | the file protocol, both directions | nothing; pure file I/O |
| `src/ap_checkdata.*` | parsing `checkdata.txt` | read once per map load |
| `src/ap_state.*` | what the client last said: unlocks, items, excluded missions | fed by `ap_bridge` |
| `src/ap_text.*` | splitting, trimming, parsing | nothing |
| `src/ap_locations.*` | firing checks: map reached, mission complete, charger, weapon | `ServerActivate`, `CBasePlayer::PlayerUse` |
| `src/ap_items.*` | the loadout, weapon refusal, armour | `CBasePlayer::Spawn`, `CGameRules::CanHavePlayerItem`, `CHalfLifeRules::CanHaveItem` |
| `src/ap_hub.*` | console commands, warps, the mission-boundary choke point | `GameDLLInit`, `CChangeLevel::ChangeLevelNow` |
| `src/ap_deathlink.*` | deaths out, deaths in | `CBasePlayer::Killed` |
| `src/ap_traps.*` | the three traps, and their precache set | `ClientPrecache`, the poll |

`ap_text`, `ap_bridge`, `ap_checkdata` and `ap_state` depend on nothing but the
C++ standard library, which is deliberate: they are the pieces that can be built
and tested without the game.

## The boot trace

`hlap/archipelago/ap_boot.txt` gets a line per hook, flushed as it is written and
truncated at `GameDLLInit`. It exists because of how this project fails: a
mistake in a hook crashes the engine during map load, and everything that would
say where -- the console, the last frame -- goes with it. The file survives, and
its last line is the last hook that ran.

A clean load reads:

    GameDLLInit: ap::RegisterCommands
      commands registered
    CWorld::Precache: ap::PrecacheTraps
      traps precached
    ServerActivate: ap::Startup
      checkdata read
      bridge open
      map start done
    CBasePlayer::Spawn: ap::ApplyLoadout
    StartFrame: first frame

The whole sequence appears twice when a new game starts, because the engine
activates the server twice. Nothing here minds: `HELLO` only asks the client for
a fresh snapshot, and every step is idempotent.

Set `kTraceLoad` in `ap_main.h` to false to switch it off. It costs a dozen line
writes per map load, so there is no hurry.

## Decisions worth knowing

**Pickups are refused in the game rules, not at the touch.**
`CGameRules::CanHavePlayerItem` and `CHalfLifeRules::CanHaveItem` are the one
question every path into the player's inventory already asks, including a weapon
handed over by `GiveNamedItem` from map logic. Refusing there leaves the entity
in the world with no pickup sound and no HUD flash, which is exactly the wanted
behaviour, and it means no fourth path can appear later and bypass the gate.
Granting sets a flag so our own `GiveNamedItem` is not refused by the rule that
exists to refuse the map's copy.

**Chargers are matched by nearest unit, not by equal coordinates.** The
generator snaps its key to a 4-unit grid so ids stay stable across
regenerations, but this side does not reproduce that rounding: the closest
charger of the same classname in the same map wins, within 32 units. Two
chargers of the same classname are never closer than 204 units anywhere in the
campaign, and any two chargers are never closer than 48, so the match cannot be
ambiguous -- and a future recompile that shifts a brush slightly cannot break it.

**The hub is `stalkyard` until there is an authored map,** and it is also
`startmap` in `liblist.gam`, so New Game begins there rather than on the tram.
It was picked against the map files: no `trigger_changelevel` (`lambda_bunker`
has one into the middle of Forget About Freeman), nothing that hurts you while
you stand still (`pool_party` has a `dmg 200` trigger), and small, because it is
reloaded after every mission. v2 replaces it with one room and a button per
mission.

**Commands arrive from two places and are handled in one.** `ClientCommand`
intercepts `say` and `say_team`, so a line starting with `!` or `/` is answered
and never broadcast; the console commands are the same names with `ap_` in front.
`Dispatch` in `ap_hub.cpp` is the single table both go through, so a command
cannot exist on one surface and not the other. Single-player chat has nobody else
in it, but it opens with one key and does not pause the game.

**The loadout has to be exactly idempotent**, because it runs on every spawn and
every snapshot change -- which is every check the player sends. The trap here is
retail's duplicate classnames: `weapon_mp5` and `weapon_9mmAR` are the same gun,
its maps place both, and the SDK recognises a duplicate *by classname*. Granting
the spelling the player does not happen to be holding therefore adds a second
copy of the weapon and pays out another full load of ammo, over and over. Held
under any of its names counts as held, and the whole list is checked before
anything is granted.

**A granted weapon needs the client told about it.** A weapon reaches the HUD's
selection buckets through the `WeapPickup` message its own `AddToPlayer` sends,
and handing one over outside the ordinary flow of walking onto it misses that.
The result is a weapon the server has and the HUD does not: unselectable with the
slot keys, though `lastinv` still reaches it, because that is decided
server-side. `ApplyLoadout` calls `ForceClientDllUpdate` after a real grant --
the SDK's own repair, and what `fullupdate` does.

**`ap_warp` takes a part number, and only for parts already reached.**
`ap_warp unforeseen 6` is a way back into a mission after a death or an errand in
the hub. It is deliberately not a way past a mission's first half: the checks in
a part skipped to would be free, and warping to the last part would be the
fastest route through any mission. "Already reached" is answered by that map's
own `map_reached` check being in the client's `checked` list, which is the one
record that survives a restart and a reconnect.

**Everything the player is told goes through `Notify`,** which reaches the HUD's
message area and the console. `Say` is console-only and is for the answer to a
command -- `ap` is eighteen lines and does not belong across the screen. Weapons
and mission unlocks arrive in the *snapshot* rather than as events, so the poll
diffs each new snapshot against the last to find them; without that they arrived
in complete silence.

**Butterfingers really drops the weapon.** `CBasePlayer::DropPlayerItem` begins
`if ( !g_pGameRules->IsMultiplayer() ) return;`, so the trap removes the weapon
and throws a fresh copy on the floor instead. It can be picked back up -- that
goes through the normal gate and passes, since the multiworld did send it -- and
the suit reissues after 30 seconds otherwise. The loadout has to be told to skip
a withheld weapon, or it would hand it straight back on the next snapshot
change, which is any check the player sends.

## Rules that are not negotiable

- **Never do anything to the engine from inside a hook.** Decide in the hook,
  act in `StartFrame`. Two of these have already been paid for:
  - A level change issued from inside code the engine is already running a level
    change through is a crash. `RequestMap` sets a string and `RunDeferred` acts
    on it next frame -- from console commands too, which look safe and are not.
    This is the hardest-won rule from the Sven Co-op project.
  - A user message written from `CBasePlayer::Killed`, or from `Spawn` before
    the client is in the server, is
    `SZ_GetSpace: Tried to write to an uninitialized sizebuf_t` and a dead game.
    `Notify` queues; `FlushNotices` sends. That one cost a crash on the first
    death of the first real playthrough.
- **The suit is granted, never removed.** It owns the weapon HUD and weapon
  switching; a player without it cannot use what they have. The `HEV Suit` item
  controls armour, which is clamped to zero every frame until it arrives.
- **Warps use `map`, not `changelevel`.** A clean load with no carried state is
  what makes a mission repeatable and independent. Transitions *inside* a mission
  stay the game's own.
- **Hold nothing across a save.** The client's snapshot is reapplied on spawn, so
  a quickload cannot desync. A re-sent check is a no-op on the server. The one
  exception is `ap_amnesty.txt`, and only because the death message has to name
  the remaining allowance at the instant of the death.
- **Precache everything a trap can spawn, at map load.** GoldSrc fatally errors
  on an unprecached model and the precache table is finite.

## Known map facts worth knowing before Phase 4

- `c2a3d` (Apprehension) has a `player_weaponstrip`: the game takes the player's
  weapons mid-mission and the loadout has to survive that. It does, in principle
  -- the loadout is reapplied whenever the snapshot changes, and on every spawn
  -- but this is the case to test first.
- `c5a1` (Endgame) has one too, which is fine: it is the ending.
- There is no `game_player_equip` anywhere in the campaign.
- There is no `item_suit` entity anywhere in the campaign either, so the HEV suit
  is granted some other way in `c1a0d`. Find out how before trusting the armour
  gate.
