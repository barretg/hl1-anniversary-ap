# The game side: `hlap`

A Half-Life server dll, built from Valve's own SDK, that talks to the
Archipelago client through the file bridge in `<Half-Life>/hlap/archipelago/`.

**Status: it loads and runs.** Phase 0 is done. The dll builds as 32-bit with
MinGW gcc 16.2 (100 SDK sources plus our ten), installs through
`tools/install_mod.py`, and the anniversary client loads it: `hl.exe -game hlap`
starts `c0a0` through the fallback, every hook fires in order, `checkdata.txt`
parses, and `HELLO|c0a0` lands in `ap_out.txt`.

What has *not* been exercised is a real seed: checks firing, weapons being
refused, warps, the mission-boundary interception. All of that is inert until the
client connects, by design -- `ap::Live()` is false without a snapshot, and the
game stays out of the way rather than sending checks into the void.

The headless route, `hlds.exe -game hlap +map c0a0`, is not available: the
dedicated server shipped inside a Steam client install cannot mount its
filesystem, and the stock `valve` game fails identically, so it says nothing
about this dll either way. Test in the real client.

## Why a dll rather than a plugin

Valve's [ValveSoftware/halflife](https://github.com/ValveSoftware/halflife)
repository tracks the 25th anniversary game, so a dll built from it is the
shipped game's own logic rather than the 2003 SDK's. That is what makes this
acceptable to a player who specifically wants the original game, and it gives
full C++ class access -- `GiveNamedItem`, `RemovePlayerItem`, `PlayerUse`,
`CanHavePlayerItem` -- with no third-party dependency.

The mod folder inherits everything else through `fallback_dir "valve"`, so the
player's install is never written to. See `apworld/half_life/mod/` for the
installer and `liblist.gam`.

## Building

    git clone https://github.com/ValveSoftware/halflife.git ../halflife
    git -C ../halflife apply ../hl1-anniversary-ap/game/sdk.patch

With MinGW, which is what it has actually been built with. MSYS2's 32-bit gcc:
`pacman -S mingw-w64-i686-gcc mingw-w64-i686-make`.

    cmake -S game -B build/game -G "MinGW Makefiles" -DHLSDK_DIR=../halflife \
          -DCMAKE_C_COMPILER=C:/msys64/mingw32/bin/gcc.exe \
          -DCMAKE_CXX_COMPILER=C:/msys64/mingw32/bin/g++.exe \
          -DCMAKE_MAKE_PROGRAM=C:/msys64/mingw32/bin/mingw32-make.exe
    cmake --build build/game -j 8

With MSVC, which nobody has tried yet:

    cmake -S game -B build/game -A Win32 -DHLSDK_DIR=../halflife
    cmake --build build/game --config Release

The result is `hl.dll`, about 2.7 MB stripped, which goes to
`<Half-Life>/hlap/dlls/hl.dll`. Dropping it into
`apworld/half_life/mod/files/dlls/` makes the apworld install it for the player;
that path is gitignored, so a development checkout installs everything but the
dll and the client says so.

32-bit is not optional: GoldSrc loads a 32-bit dll.

`sdk.patch` was generated by editing a clean clone, so it applies cleanly by
construction: 45 added lines across seven files, one `#include` and one call per
hook, nothing of Valve's deleted. Keeping it that small is the point -- the less
this project edits Valve's files, the less a future SDK update costs.

### What building with MinGW cost

Four things, all of them small and all of them recorded rather than worked
around silently:

- `cbase.h` and `util.h` spell the export attribute `_declspec`, which is MSVC
  only. Both sit behind an `#ifndef`, so the CMakeLists defines
  `CBASE_DLLEXPORT` and `UTIL_DLLEXPORT` to `__declspec(dllexport)` for
  non-MSVC and Valve's headers are untouched.
- `common/mathlib.h` has an MSVC inline-asm block behind `#ifdef _WIN32`, with a
  portable C branch right beneath it. `sdk.patch` narrows that to
  `defined(_WIN32) && defined(_MSC_VER)`, so MSVC keeps the asm and everyone
  else gets the C. This is the only patch hunk that is not a hook.
- gcc 16 defaults to C23, where `false` is a keyword and `const.h` uses it as an
  enumerator, so the three `pm_shared` C files are built as `gnu17`.
- GNU ld cannot parse the `SECTIONS .data READ WRITE` clause at the end of the
  SDK's `dlls/hl.def`, so the MinGW build uses `hl_mingw.def` instead. See the
  comments in that file: it exists for exactly one export.

The link is fully static. `-static-libgcc -static-libstdc++` is not enough --
the posix-threads build of gcc still imports `libwinpthread-1.dll`, a player's
Half-Life folder does not have one, and the engine reports that as
`LoadLibrary failed (126)` with no clue as to which dependency is missing.

## Layout

| File | What it owns | Where it attaches |
| --- | --- | --- |
| `src/ap_main.*` | wiring, the poll clock, the façade the patch calls | `ServerActivate`, `StartFrame` |
| `src/ap_bridge.*` | the file protocol, both directions | nothing; pure file I/O |
| `src/ap_checkdata.*` | parsing `checkdata.txt` | read once per map load |
| `src/ap_state.*` | what the client last said: unlocks, items, excluded missions | fed by `ap_bridge` |
| `src/ap_text.*` | splitting, trimming, parsing | nothing |
| `src/ap_locations.*` | firing checks: map reached, mission complete, charger, weapon | `ServerActivate`, `CBasePlayer::PlayerUse` |
| `src/ap_items.*` | the loadout, weapon refusal, armour | `CBasePlayer::Spawn`, `CGameRules::CanHavePlayerItem`, `CHalfLifeRules::CanHaveItem` |
| `src/ap_hub.*` | console commands, warps, the mission-boundary choke point | `GameDLLInit`, `CChangeLevel::ChangeLevelNow` |
| `src/ap_deathlink.*` | deaths out, deaths in | `CBasePlayer::Killed` |
| `src/ap_traps.*` | the three traps, and their precache set | `ClientPrecache`, the poll |

`ap_text`, `ap_bridge`, `ap_checkdata` and `ap_state` depend on nothing but the
C++ standard library, which is deliberate: they are the pieces that can be built
and tested without the game.

## The boot trace

`hlap/archipelago/ap_boot.txt` gets a line per hook, flushed as it is written and
truncated at `GameDLLInit`. It exists because of how this project fails: a
mistake in a hook crashes the engine during map load, and everything that would
say where -- the console, the last frame -- goes with it. The file survives, and
its last line is the last hook that ran.

A clean load reads:

    GameDLLInit: ap::RegisterCommands
      commands registered
    CWorld::Precache: ap::PrecacheTraps
      traps precached
    ServerActivate: ap::Startup
      checkdata read
      bridge open
      map start done
    CBasePlayer::Spawn: ap::ApplyLoadout
    StartFrame: first frame

The whole sequence appears twice when a new game starts, because the engine
activates the server twice. Nothing here minds: `HELLO` only asks the client for
a fresh snapshot, and every step is idempotent.

Set `kTraceLoad` in `ap_main.h` to false to switch it off. It costs a dozen line
writes per map load, so there is no hurry.

## Decisions worth knowing

**Pickups are refused in the game rules, not at the touch.**
`CGameRules::CanHavePlayerItem` and `CHalfLifeRules::CanHaveItem` are the one
question every path into the player's inventory already asks, including a weapon
handed over by `GiveNamedItem` from map logic. Refusing there leaves the entity
in the world with no pickup sound and no HUD flash, which is exactly the wanted
behaviour, and it means no fourth path can appear later and bypass the gate.
Granting sets a flag so our own `GiveNamedItem` is not refused by the rule that
exists to refuse the map's copy.

**Chargers are matched by nearest unit, not by equal coordinates.** The
generator snaps its key to a 4-unit grid so ids stay stable across
regenerations, but this side does not reproduce that rounding: the closest
charger of the same classname in the same map wins, within 32 units. Two
chargers of the same classname are never closer than 204 units anywhere in the
campaign, and any two chargers are never closer than 48, so the match cannot be
ambiguous -- and a future recompile that shifts a brush slightly cannot break it.

**The hub is `t0a0` until there is an authored map.** It is real, small, empty
and deliberately not part of the campaign, so no check can fire there and no
mission can be completed by standing in it. v2 replaces it with one room and a
button per mission.

## Rules that are not negotiable

- **Never change level inline.** A level change issued from inside code the
  engine is already running a level change through is a crash. `RequestMap` sets
  a string and `RunDeferred` acts on it next frame -- from console commands too,
  which look safe and are not. This is the single hardest-won rule from the Sven
  Co-op project.
- **The suit is granted, never removed.** It owns the weapon HUD and weapon
  switching; a player without it cannot use what they have. The `HEV Suit` item
  controls armour, which is clamped to zero every frame until it arrives.
- **Warps use `map`, not `changelevel`.** A clean load with no carried state is
  what makes a mission repeatable and independent. Transitions *inside* a mission
  stay the game's own.
- **Hold nothing across a save.** The client's snapshot is reapplied on spawn, so
  a quickload cannot desync. A re-sent check is a no-op on the server. The one
  exception is `ap_amnesty.txt`, and only because the death message has to name
  the remaining allowance at the instant of the death.
- **Precache everything a trap can spawn, at map load.** GoldSrc fatally errors
  on an unprecached model and the precache table is finite.

## Known map facts worth knowing before Phase 4

- `c2a3d` (Apprehension) has a `player_weaponstrip`: the game takes the player's
  weapons mid-mission and the loadout has to survive that. It does, in principle
  -- the loadout is reapplied whenever the snapshot changes, and on every spawn
  -- but this is the case to test first.
- `c5a1` (Endgame) has one too, which is fine: it is the ending.
- There is no `game_player_equip` anywhere in the campaign.
- There is no `item_suit` entity anywhere in the campaign either, so the HEV suit
  is granted some other way in `c1a0d`. Find out how before trusting the armour
  gate.
