# A Half-Life: Source game side: the plan

Branch: `hl-source`. Everything in this plan lives under `hl-source/` at the
repo root (see "Isolation"). Goal: play a seed generated by this apworld in
**Half-Life: Source** (HL:S, Steam app 280) instead of retail GoldSrc Half-Life,
with no change to generation, location ids or the multiworld's view of the slot.
It is a deliberate stepping stone: every Source-engine problem an HL2 apworld
will have (hook surface, delivery, saves, HUD text, commands, a hub map, BSP v19+
tooling) gets solved here first against a world whose logic is already finished
and tested.

## What "fully compatible" means

1. **Same apworld, same seed.** A seed generated today plays in HL:S. No new
   options, no new location ids, `data_version` unchanged. A player could start
   a slot in GoldSrc and finish it in HL:S.
2. **Same client, same bridge.** The Python client and the file protocol in
   `docs/protocol.md` are reused as is. The HL:S game side reads the same
   `checkdata.txt` and `ap_in.txt` and writes the same `ap_out.txt`.
3. **Same player-facing behaviour** wherever the engine allows it: hub, `!warp`,
   warp points, pickup refusal, checks, DeathLink with amnesty, traps, `!find`,
   `!tracker`. Where Source cannot match, the gap is listed below and the
   behaviour degrades safely (a check that cannot fire is a bug; a cosmetic that
   cannot be shown is a known gap).
4. **Half-Life only.** HL:S has no Opposing Force or Blue Shift, and no
   content from either is ever attempted in HL:S. A seed that includes them
   treats those missions exactly as an install without those games does today:
   refused with that reason, and the client warns on connect. See "Half-Life
   content only".

## Facts checked on this machine

Against `steamapps/common/Half-Life 2/hl1` (HL:S ships inside the Half-Life 2
install, not as its own folder):

- **32-bit.** `hl1/bin/server.dll`, `client.dll` and `bin/engine.dll` are PE32
  i386. The existing clang-cl / lld-link / xwin x86 toolchain applies unchanged.
- **Source SDK 2013 singleplayer era interfaces.** Engine exposes
  `ISERVERPLUGINCALLBACKS003`, `ISERVERPLUGINHELPERS001`, `VEngineServer021`,
  `GAMEEVENTSMANAGER002`; the game dll exposes `ServerGameDLL009`,
  `ServerGameEnts001`, `ServerGameClients004`, `PlayerInfoManager002`,
  `VSERVERTOOLS002`, `EngineTraceServer003`. Public SDK 2013 headers match these.
- **Every map the campaign uses exists.** All 96 Half-Life maps named in the `C`
  records are in `hl1/maps`, same names, `VBSP` version 19.
- **Chargers are still brush entities.** `func_healthcharger` and
  `func_recharge` exist with the same per-map counts sampled (c1a1a, c2a3d), so
  the position-keyed charger ids can carry over.
- **`player_weaponstrip` survives** in c2a3d, so the same mid-mission strip case
  applies.
- **No game source.** Valve has not published HL:S's game code. `server.so` is
  stripped (218 dynamic symbols, no vtables), but `server.dll` carries MSVC RTTI
  for the classes we care about: `CHL1_Player`, `CHalfLife1`, `CWallHealth`,
  `CRecharge`, `CTriggerHurt`, `CChangeLevel`, `CRevertSaved`,
  `CBaseHL1CombatWeapon`.
- **Game events** `player_death`, `player_hurt` and `player_spawn` are present.
  There is no `item_pickup` event.
- `hl1/gameinfo.txt` uses `gamebin hl1/bin` and `|all_source_engine_paths|`, so
  a separate mod folder can mount HL:S's content and binaries.

## Isolation

The whole project lives in `hl-source/`, and **nothing outside that folder
needs it.** Deleting `hl-source/` leaves the repo building, testing,
packaging and playing exactly as before; the only visible difference is that
`/setsourcedir`, `/sourcemode`, `/installsource` and `/uninstallsource` report
that Source support is not included in this build.

`hl-source/` may import, compile or read anything in the main project (the
portable C++ core, `bridge.py`, `checkdata.txt`, `campaign.json`, the hub
constants). The reverse is limited to two optional touch points, both of which
treat a missing or unbuilt `hl-source/` as "no Source support" and carry on:

- `tools/build_apworld.py` packages Source content only when a viable build is
  present (see Packaging).
- The client's guarded import of the backend module.

Main-project tests and the GoldSrc CMake never look inside it.

```
hl-source/
  README.md                  how to build, install and test
  docs/HL_SOURCE_PLAN.md     this file
  plugin/                    the VSP: CMakeLists, src/, engine adapter
  client/                    hlsource_backend.py: the Source engine backend
  mod/                       gameinfo.txt, addons/hlap.vdf, cfg, the hub VBSP
  tools/                     source_rtti.py, verify_source_maps.py
  tests/                     its own pytest suite and aptest scenarios
```

## Packaging

`tools/build_apworld.py` packages Source support when, and only when, a viable
Source build is present, and excludes all `hl-source/` content otherwise. The
GoldSrc rules (refuse without a staged `hl.dll` unless `--allow-no-dll`) are
unchanged.

A build is **viable** when all of these hold:

- `hl-source/` exists.
- The plugin dll is staged at `hl-source/mod/files/addons/hlap.dll`
  (gitignored, staged by the plugin's CMake build exactly as the GoldSrc build
  stages `hl.dll`).
- That file is a PE32 i386 dll exporting `CreateInterface`, so a stale or
  wrong-architecture file is not shipped as working.

When viable, the build adds to the `.apworld`, under `half_life/`:

- `client/hlsource_backend.py`, the backend module.
- `mod_source/`, the Source mod tree: `gameinfo.txt`, `addons/hlap.vdf`,
  `addons/hlap.dll`, cfg, the hub VBSP, and the HL:S translation table.

When not viable, none of it is added, and the build prints one line saying why
(no `hl-source/`, no staged plugin, or a staged file that failed the check). It
is not an error. `--no-source` forces the exclusion for a release that should
not carry it.

The client looks for `half_life.client.hlsource_backend` with a guarded import.
Present, the Source commands work; absent, they refuse cleanly. The backend
reads its mod tree from the packaged `mod_source/`, never from the repo.

## Half-Life content only

No Opposing Force or Blue Shift weapon, item, entity, model, sound or map is
ever granted, spawned, gated, precached or pointed at in HL:S. The seed may
still carry them, because the seed is shared with GoldSrc, so the plugin filters
at the point of reading rather than trusting the data:

- `checkdata.txt`: only the `C`, `L`, `K`, `S` and `M` records belonging to the
  `half_life` game (and the hub) are loaded. Other games' `N` records are kept
  only to name them as unavailable.
- `items`, `starting` and `ungated` from the snapshot are filtered against
  Half-Life's own classname and item set. Opposing Force weapons (Desert Eagle,
  M249, Sniper Rifle, Displacer, Spore Launcher, Barnacle Grapple, Shock Roach),
  the combat knife, the pipe wrench, the PCV and the Security Armor are
  dropped silently.
- **The crowbar is always granted.** When the seed's starting melee is the
  combat knife or pipe wrench, HL:S starts with the crowbar anyway, even though
  that seed treats the crowbar as an item. Melee gates nothing in logic, and the
  bridge must never leave the player without a melee weapon. The crowbar's own
  `First Crowbar` check still fires the normal way.
- OF/BS missions, checks and items show in `ap`, `!tracker` and `!find` as "not
  available in Half-Life: Source", as an install without those games shows
  them today. `!warp` refuses them with that reason.
- Traps spawn only Half-Life NPCs.

`hl-source/tests/` feeds a snapshot from a seed with all three games through the
plugin's filter (it sits beside the portable C++ core, so it builds without the
game) and asserts that no non-Half-Life classname gets through and that the
crowbar is in the starting set.

## Decision 1: the hook surface

GoldSrc got its hooks by rebuilding Valve's published SDK with a 64-line patch.
HL:S has no published game source, so that route is closed. Options:

- **Rebuild an HL1 server.dll on Source SDK 2013.** Rejected: it means
  reimplementing every HL1 entity, NPC and weapon. That is a total-conversion
  project, not a client.
- **SourceMod + Metamod:Source.** Rejected as a dependency: SourceMod has no
  gamedata for single-player HL:S, adds two third-party installs for the player,
  and its scripting layer buys nothing over C++ here.
- **Our own Valve Server Plugin (VSP), in C++.** Chosen. It loads into the stock
  game through `addons/*.vdf`, gets the engine's plugin callbacks, and reaches
  game objects through the interfaces listed above. Where a callback is not
  enough, it hooks a single virtual by patching a vtable slot found through
  RTTI.

The order of preference for every hook, cheapest and safest first:

1. **A plugin callback or game event.** `LevelInit`, `ServerActivate`,
   `GameFrame`, `LevelShutdown`, `ClientPutInServer`, `ClientCommand` (with
   `PLUGIN_STOP` to swallow `say !cmd`), `player_death`, `player_spawn`.
2. **Runtime introspection, no offsets.** Fields are found by name through
   `ServerClass` send tables and `datamap_t` (`m_iHealth`, `m_ArmorValue`,
   `m_hMyWeapons`, `m_iszGlobalName`, `m_flDamage`, `m_bitsDamageInflicted`).
   Entities are created and spawned through `IServerTools`
   (`CreateEntityByName`, `DispatchSpawn`, `SetKeyValue`).
3. **Polling the world each frame** instead of hooking, where the cost is
   trivial: inventory diff for weapon pickups, point-in-volume for healing pools.
4. **A vtable slot on an engine interface we already hold.** Hooking
   `IVEngineServer::ChangeLevel` intercepts mission boundaries without touching
   game code.
5. **A vtable slot on a game class**, located by RTTI, with the slot index taken
   from SDK 2013 headers and confirmed against the binary. Kept to the few
   decisions that must happen *before* the game acts: pickup refusal and charger
   use.

No byte-signature scanning and no inline detours in the first cut. Both break on
any game update; RTTI vtable lookup plus header indices breaks only if Valve
reorders the base classes, which the 2013 branch has not done.

`hl-source/tools/source_rtti.py` dumps the vtables of the RTTI classes above from
`server.dll` into a generated header, so a game update is a regenerate and a
diff, not a hunt.

## Decision 2: delivery

The GoldSrc mod lives in its own `hlap` folder and never writes to the player's
game. The Source side keeps that rule when it can, and is allowed to break it
when it cannot.

**Preferred: a sourcemod with linked binaries.**
`<Steam>/steamapps/sourcemods/hlap_source/` holds:

- `gameinfo.txt` mounting HL:S content through `|all_source_engine_paths|hl1`
  and HL2's shared VPKs, the same search paths as the stock `hl1/gameinfo.txt`.
- `bin/server.dll` and `bin/client.dll`: HL:S's own, **unmodified**, hardlinked
  from `hl1/bin` (copied when on another drive), using the same link-or-copy
  code as `apworld/half_life/mod/content.py`. Having them in our own `bin/`
  removes the question of whether a sourcemod can borrow another game's
  binaries.
- `addons/hlap.vdf` and `addons/hlap.dll`: the plugin.
- `custom/`: our content, including the hub.
- `archipelago/`: the bridge.

It is launched with the Half-Life 2 install's own `hl2.exe -game <mod>`, not
through Source SDK Base 2013, because HL:S's `server.dll` only matches the
interfaces of HL2's engine (verified: `ServerGameDLL009`, `VEngineServer021`).
That also means `|all_source_engine_paths|` resolves to the real install, so
the content VPKs (several GB with HL2's) are mounted, never copied.

**Staleness.** A Valve update can replace `hl1/bin`, leaving a copied or
hardlinked dll that no longer matches the engine. `/installsource` records the
source files' hashes; the client checks them on start in Source mode and tells
the player to rerun `/installsource` when they have changed.

**Fallback, approved:** if Phase 0 shows the sourcemod cannot work, install
into `Half-Life 2/hl1/custom/hlap/` (a folder the stock `gameinfo.txt` already
mounts) plus `hl1/addons/hlap.vdf` and `hl1/addons/hlap.dll`. That writes into
the install, so `/uninstallsource` removes exactly those paths, and the setup
docs say so.

The bridge directory is `<mod folder>/archipelago/` in either case, with
identical file names.

## Decision 3: Half-Life by default, Source only when the player asks

The client stays a GoldSrc client unless the player turns Source on. The Source
install is **never inferred**: nothing is auto-detected, guessed or derived from
the Half-Life folder, and both new settings default to off and empty until the
player sets them.

| Setting (host.yaml) | Default | Set only by |
| --- | --- | --- |
| `source_mode` | `false` | `/sourcemode` |
| `source_game_folder` | `""` | `/setsourcedir` |

An older `host.yaml` without these keys reads as the defaults, so existing
installs behave exactly as today. The existing GoldSrc path handling
(`game_folder`, `--gamedir`, `/gamedir`, auto-detection of the Half-Life
install) is not touched by this project and plays no part in Source mode:
`/gamedir` keeps accepting only a Half-Life install, and `/setsourcedir` is the
only way to name the HL:S one.

### Commands

| Command | Does | Needs |
| --- | --- | --- |
| `/setsourcedir <dir>` | saves the Half-Life 2 root that holds `hl1/`, after the backend validates it (`hl1/maps/c0a0.bsp`); no argument prints the current value; never turns Source mode on | backend |
| `/sourcemode <true\|false>` | `true` re-points the bridge at the Source mod's `archipelago/` folder and warns if the mod is not installed; `false` re-points it at the GoldSrc `hlap` folder; no argument prints the mode; the switch is live (bridge reopens, forced snapshot) | backend; `true` also needs a valid source dir |
| `/installsource` | installs the packaged Source mod into the source dir, reporting the Decision 2 route used and how to launch | backend, source dir |
| `/uninstallsource` | removes the Source mod, its bridge files and its warp-point saves from the source dir, naming what went; the player's own HL:S saves are left alone | backend, source dir |

`/installsource` and `/uninstallsource` work with Source mode on or off, so the
mod can be installed before switching. `/install` and `/uninstall` keep meaning
the GoldSrc mod only and are unchanged.

While Source mode is on, the remaining engine-specific behaviour routes to the
backend: `/where` (which also names the engine), the missing-games warning
(Opposing Force and Blue Shift are always reported as unavailable) and the
warp-save sweep when the slot goals. Everything else, including every line of
the protocol, is shared. `tests/test_bridge.py` passes untouched.

**Without the backend** (a build where Source content was excluded) all four
Source commands say "Source support is not included in this build" and change
nothing. A `host.yaml` that has `source_mode: true` from a Source build, loaded
by a normal build, logs that warning once and runs in GoldSrc mode rather than
failing to start.

### The backend module

`hlsource_backend.py` implements:

| Method | Source behaviour |
| --- | --- |
| `detect(root)` | `hl1/maps/c0a0.bsp` under the given root (validation only, never a search) |
| `mod_dir(root)` | the sourcemods folder, or `hl1/custom/hlap` (Decision 2) |
| `store_dir(root)` | `<mod>/archipelago` |
| `save_dir(root)` | `<mod>/save` |
| `install(root)` | the packaged `mod_source/` tree; backs `/installsource` |
| `uninstall(root)` | removes exactly what `install` wrote; backs `/uninstallsource` |
| `campaigns(root)` | Half-Life only |
| `launch_hint()` | how to start the mod |

The warp-save key (`ap<fnv>_...`) and `ap_amnesty.txt` are engine-agnostic;
only the directory differs.

The main project gains only the guarded import, the two settings, the four
commands, and the optional packaging step. Its tests cover the no-backend path
(the commands refuse, settings default, a stale `source_mode: true` falls back)
and packaging with no viable build (nothing from `hl-source/` in the zip),
using a temporary repo layout rather than the real folder. Tests of the
backend-present path live in `hl-source/tests/`.

## Testing

`hl-source/tests/` is its own suite, run with
`python -m pytest hl-source/tests -q` and never collected by the main
`python -m pytest tests`. It and the Source mock client find the local HL:S
install automatically, by the same convention `tests/test_completion_safeguards.py`
uses for Half-Life: a `DEFAULT_SOURCE_ROOT` of
`/mnt/win/f/SteamLibrary/steamapps/common/Half-Life 2`, overridden by the
`HLS_ROOT` environment variable, and install-dependent tests skip when it is
absent.

The mock client is `hl-source/tests/aptest/aptest_source.py`, a thin wrapper
that imports `tests/aptest/aptest.py`'s scenarios and harness, defaults
`--game-root` to the Source install, takes the bridge directory and map paths
from the backend, and swaps the test build of the plugin into the installed mod
the way the GoldSrc harness swaps `hl.dll`. Scenarios that need content HL:S
lacks (Opposing Force, Blue Shift) are filtered out. The main harness is not
modified.

## Decision 4: proving the data holds in HL:S

Location ids are keyed by map and, for chargers, by world position read from
GoldSrc BSPs. HL:S maps are conversions, so this must be **checked, not
assumed**. New `hl-source/tools/verify_source_maps.py` reads every HL:S `.bsp` (VBSP
entity lump 0, models lump 14, the same indices as GoldSrc) and fails if any `L`
record has no counterpart:

- `charger`: a same-classname unit within 32 units (the game side's own match
  radius); report the worst distance found.
- healing pools: a `trigger_hurt` with negative `damage` at the same spot.
- `weapon_pickup`: the classname present on that map.
- `map_reached` / `chapter_complete`: the map exists and the same
  `trigger_changelevel` map/landmark pairs exist (the mission boundary depends
  on them).
- `P` and `M` records: covered by the hub rebuild and the Gonarch check.

Any mismatch becomes an HL:S-side translation table in `hl-source/data/`,
shipped with the plugin and applied by it, never a change to an id or to
`checkdata.txt`. Logic facts that depend on map geometry
(`unreachable_copies`, `weapon_source_gates`, crates only an explosive clears)
are re-verified with the aptest scenarios once the plugin runs; HL:S physics
differs from GoldSrc in places, and any HL:S-only gap is raised before it is
encoded, since it would affect generation for every player.

## Decision 5: the hub

`ap_lobby_alpha` is a GoldSrc BSP. Porting the authored source is possible
(Source Hammer can usually open GoldSrc `.rmf`/`.map`; geometry and entity
names come across, textures and lighting must be redone) but it needs the
mapmaker, and the files are not on hand. The hub is therefore done in two
stages with one contract: entrances named `chapter_<n>_button` (a
`func_button`, `trigger_once` or `trigger_multiple`), so the generator's `P`
records and the gate code apply unchanged.

1. **Interim, generated.** `hl-source/tools/build_source_hub.py` writes a VMF
   from `campaign.json`: a plain room with one trigger entrance per Half-Life
   mission, each labelled with world text, a player start and light entities.
   It compiles with the `vbsp`/`vvis`/`vrad` shipped in the Half-Life 2 `bin/`.
   Adding a mission regenerates the room.

   **It must compile with no leak**, so `vvis` runs a real visibility pass and
   `vrad` produces lightmaps rather than fullbright. The generator builds a
   sealed hull of solid world brushes enclosing every entity, with no entity
   origin on or outside it. The build fails, rather than shipping a fullbright
   map, if `vbsp` reports a leak or leaves a `.lin` pointfile, or if `vvis` or
   `vrad` exits non-zero. A test asserts every generated entity origin is
   strictly inside the hull.
2. **Authored, later.** The mapmaker's port replaces it when available, under
   the same no-leak build check.

A test in `hl-source/tests/` checks the Source hub's name and entrances against
the main project's `hub_map` and `P` records, so the main-project four-names
test stays as it is.

## Phases

**Phase 0: spikes (decides Decisions 1 and 2).**
- A hello-world VSP built with clang-cl against SDK 2013 headers loads in HL:S
  single-player and prints from `GameFrame`.
- The sourcemod, with linked `bin/` dlls, launched by `hl2.exe -game`, boots
  HL:S content with our `addons/` plugin loaded.
- RTTI dump of `server.dll`; one vtable hook (`CanHavePlayerItem`) refuses a
  weapon pickup in c1a0.
Exit: all three work, or the fallback install path is chosen with the user.

**Phase 1: data and client.**
- `hl-source/tools/verify_source_maps.py`, run against the install, report read.
- Main project: the two settings, `/setsourcedir`, `/sourcemode`, the guarded
  backend import, and no-backend tests. Existing tests unchanged and green.
- Main project: `/installsource`, `/uninstallsource`, and the viability
  check and optional packaging in `tools/build_apworld.py`.
- `hl-source/`: `hlsource_backend.py`, its installer, and backend-present tests,
  including a packaging test that a viable staged dll lands in the zip.
- Isolation check: with `hl-source/` moved aside, the main suite passes and
  `tools/build_apworld.py` builds an apworld with no Source content.

**Phase 2: bridge and locations.** Plugin compiles the portable core; `HELLO`,
snapshot parse, authorisation, all three check types, mission boundaries, warps,
warp points, and the generated hub (every mission boundary returns to it). A
seed's checks fire end to end with the real client.

**Phase 3: items and gates.** Loadout, refusal, armour, `starting`, `ungated`,
the c2a3d weapon strip, filler events.

**Phase 4: DeathLink and traps.** DeathLink both ways with amnesty, the trap
set, Half-Life NPCs only.

**Phase 5: parity pass.** Run `aptest_source.py`'s `--parity`, `--find` and
`--trace` scenarios against the plugin, then a full playthrough.

## Risks, in the order they can hurt

1. **Pickup refusal via vtable hook is wrong or unstable.** It is the one hook
   every gate depends on. Mitigation: Phase 0 proves it before anything else is
   built.
2. **Map conversions moved things.** A charger outside the 32-unit radius never
   fires. Mitigation: Decision 4's tool, before any play.
3. **Logic does not hold in HL:S geometry or physics.** Mitigation: aptest
   re-run; HL:S-only differences raised with the user before touching shared
   logic.
4. **Sourcemod delivery does not work.** Mitigation: the approved `custom/`
   plus `addons/` fallback.
5. **A game update moves vtables.** Mitigation: regenerate from RTTI; the
   plugin checks the RTTI name of every object it hooks and refuses to hook
   (logging to the boot trace) rather than call a wrong slot.
6. **Reliable channel overflow** carries over from GoldSrc; the same queue and
   per-frame cap apply.

## What carries to HL2

- The plugin skeleton, engine adapter, text queue, commands, boot trace,
  save-based warp points, the `ChangeLevel` interception, game events and
  introspection-based field access.
- The optional-backend pattern in the client, the sourcemod installer, and VBSP tooling
  (`verify_source_maps.py` generalises into HL2's map reader).
- HL2 does have public game code (SDK 2013), so HL2 can choose between this
  plugin and a rebuilt server dll; the plugin core keeps that choice open, and
  the portable four (`ap_text`, `ap_bridge`, `ap_checkdata`, `ap_state`) move
  either way.

## Decisions settled with the user

- Seeds are unaware of the engine: nothing in generation, options or slot data
  knows HL:S exists.
- The hub is generated now, leak-free; the authored port follows when the
  mapmaker supplies the source.
- The `hl1/custom` plus `hl1/addons` fallback is acceptable.
- The crowbar is always granted in HL:S.
- Melee throw and the Bot Swarm trap are revisited after the initial
  implementation. Release timing is the user's call.
